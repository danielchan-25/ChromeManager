# ChromeManager Linux 移植方案

日期：2026-10-27。目标：Ubuntu 24.04 LTS amd64、Python 3.12、普通专用用户、Chrome Stable，默认保留有界面浏览器。此项目独立于 Windows 源目录，禁止复制或提交生产数据库、浏览器 Profile、Cookie、日志、密钥或机器配置。

## 1. 首版范围与验收

- 保留中文 Web 页面、实例元数据、独立 Profile、代理、默认网址、备份/恢复、资源与 CDP 检查。
- Web 默认 `0.0.0.0:8765`、无密码；每个实例保持固定公开 CDP 端口，Chrome 只监听独立本机内部端口。
- 启停、正常退出、浏览器自行重启和重新接管均核验 PID、进程创建时间、绝对数据路径及 CDP 返回的浏览器身份。
- systemd 部署中每个浏览器使用独立用户服务单元；Web、转发、显示服务分别托管。重启 Web 不应停止浏览器或已经建立的 CDP 连接。
- Chrome 退出原因、启动参数、操作关联 ID、异常、转发失败写本机 UTF-8 轮转日志；不包含飞书或其他通知功能。
- 导入工具仅从 Windows 数据库导入元数据，在目标创建新 Profile；不迁移运行会话、旧 PID、Windows 路径或浏览器凭据。
- 自动化验证包括：两个实例并发、HTTP 与 WebSocket 转发、错误 PID 拒绝、转发端口冲突隔离、手动停止不自动复活、浏览器重新接管、导入回滚和启动失败可重试。
- Ubuntu 容器可以验证 Linux 代码、真实 Chrome 与转发；真实主机开机、systemd 用户会话、显示/密钥环及网站登录需列为主机验收，不能用单元测试代替。

## 2. Windows 故障与设计决策

| 已发生问题 | Linux 首版措施 |
| --- | --- |
| 前台窗口关闭，服务和实例长时间离线 | systemd 启动与恢复；保留日志和服务退出码；手动 systemctl stop 不触发强行复活 |
| DB 显示运行中、Chrome 实际已退出 | 启动时以及定期核对实际进程；重新接管通过 CDP 验证；过期会话关闭 |
| Chrome 自行更新/重启，PID 改变 | 用绝对 Profile 路径和内部端口寻找唯一根进程，不依赖 Windows 进程名 |
| CDP 与 wildcard 转发抢同一个端口 | 固定公开端口与持久化内部端口隔离；不在 Chrome 原生端口上建立 wildcard 监听 |
| IP Helper 停止、UAC 无法确认 | 使用普通用户可运行的独立 TCP 转发服务，不依赖 netsh、注册表或管理员轮询 |
| 一个端口转发出错影响其他实例 | 每个公开端口独立绑定/重试，逐端口报告失败；校验目标身份后转发 |
| 高 CPU 下连接表扫描耗尽健康检查预算 | 直接连接内部 CDP，协议验证 PID，不扫描整个系统连接表 |
| 乱码 console、关闭 console 导致 Chrome 异常结束 | 不调用 Win32 窗口 API；stdout/stderr 和原生日志写文件；Linux 正常退出后再做限时强制回收 |
| 管理服务重启影响正在工作的浏览器 | systemd 浏览器实例单独 cgroup，Web 不拥有它们的服务生命周期 |
| Profile 共享、Cookie 迁移异常 | 每实例独立目录；导入只迁元数据；按新平台重新登录并验证密钥环 |

## 3. 进程与网络结构

```text
systemd 用户服务（专用非 root 用户）
  ├─ chromemanager-web.service       0.0.0.0:8765
  ├─ chromemanager-relay.service     公开端口 -> 127.0.0.1:内部端口
  ├─ chromemanager-browser@4.service 独立 Chrome / Profile
  ├─ chromemanager-browser@5.service 独立 Chrome / Profile
  └─ chromemanager-browser@6.service 独立 Chrome / Profile
```

内部端口默认从 20000–29999 中持久化分配，并避开所有已登记公开/内部端口。TCP 转发保留原始 HTTP Host 和 WebSocket 字节，不记录业务消息。停止/删除实例后撤下该公开端口；转发进程重启会断开已有连接，调用方须有限重连，Web 重启则不应影响转发。

开发/容器可选 direct 模式：Chrome 独立进程会话运行。正式 systemd 部署必须使用 systemd 模式，避免直接子进程被 Web 服务停止动作连带结束。无头模式用于隔离集成测试；实际扫码、验证码使用固定显示环境。

## 4. 配置与目录

- 建议 8 vCPU / 16 GB RAM / 100 GB SSD；三个轻量实例测试可用 4 vCPU / 8 GB。
- Python 3.12 venv、Google Chrome Stable、Xvfb/轻量窗口管理器或现有 X11 桌面、D-Bus、字体和可用密钥环。
- 推荐代码 `/opt/chromemanager-linux`；数据 `/srv/chromemanager`，通过 `CHROME_MANAGER_DATA_ROOT` 指定。
- 数据包含 `data/`、`profiles/`、`logs/`、`backups/`、`config/settings.toml`，只允许专用用户写入。
- Web 和 CDP 无密码延续现有需求；防火墙按实际 LAN 网段放行 8765 和登记的公开端口，内部端口不对外开放。
- 远程桌面连接到同一个持久显示会话，断开远程客户端不等于停止显示服务；Xvfb 仅提供显示，不提供安全凭据存储。
- 运行 Chrome 使用普通用户并保留 sandbox；容器测试如采用测试专用 sandbox 例外必须明确标注，不复制为生产配置。

## 5. 分阶段实施

阶段 1–6 已完成，独立仓库为 [ChromeManager-Linux](https://github.com/danielchan-25/ChromeManager-Linux)。Ubuntu 原生自动化验证已通过，详见 [验证记录](VALIDATION.md)。阶段 7 为收到目标 Ubuntu 主机后执行的迁移验收。

1. 建立独立源代码快照，保留 MIT 版权；不复制 `.git`、venv 和生产状态。
2. Linux 平台适配：查找可执行文件、启动、进程身份、正常关闭、可选 X11 窗口操作。
3. 独立转发服务、逐端口健康状态；本机浏览器检查与公开端口检查分开。
4. systemd 单元、部署脚本、固定显示环境与首次配置指南；CLI 提供初始化、导入和服务入口。
5. 测试启动失败、PID 复用、多实例、端口占用、重启和导入；设置 Ubuntu CI。
6. 首版完成后创建独立 GitHub 仓库并推送，核验远端提交与本地内容一致。
7. 在目标 Ubuntu 实机试运行：单实例 -> 三实例 -> 外部项目并发调用 -> 故障注入 -> 48 小时观察。

## 6. 数据迁移与回退

停写时对 Windows SQLite 使用在线备份 API 或一致性快照。导入工具以只读方式打开快照，验证字段和名称，只导入未删除实例的元数据、代理和公开端口；目标发生冲突时拒绝导入并回滚本次创建。保留 Windows 环境和原 Profile，测试期间不让两个平台同时执行同一个业务任务。Ubuntu 新实例重新登录，再将调用方从原 Windows IP 切换到 Ubuntu IP。失败时切回 Windows 调用地址，不覆盖原数据。

## 7. 主机验收清单

- [ ] Ubuntu 启动后无需桌面人工登录即可按配置恢复服务；不会启动第二个管理器。
- [ ] 手动停止的实例不会因为自动恢复被重新启动。
- [ ] 重启 Web、断开 SSH/远程桌面后三个 Chrome 和转发继续工作。
- [ ] Chrome 自行重启后正确接管新 PID，无残留旧会话或 Profile 锁冲突。
- [ ] 所有公开端口在另一台 LAN 主机上验证 `/json/version`、页面 WebSocket 和 `Browser.getVersion`。
- [ ] 错误端口或错误进程不能被接管、停止或转发。
- [ ] 单实例卡死、公开端口被占用时，其他实例仍能被外部项目正常使用。
- [ ] 主机重启后密钥环可用、登录保持策略明确，扫码和验证码可人工完成。
- [ ] CPU/内存压力、网站超时与 CDP 失效分别记录；不因一个探测超时自动重启业务浏览器。
- [ ] 48 小时观察期间无未解释的进程消失、资源持续增长或状态长期不一致。

## 8. 首版限制

不承诺跨系统 Cookie/密码无损迁移，不提供指纹伪装或网站风控规避，不把短暂 CDP 超时自动转换成浏览器重启。X11 窗口前台操作为可选功能，Wayland 下不承诺相同的窗口控制能力。首次发布必须在验证报告中区分本地单元测试、Linux 容器实测和仍待 Ubuntu 主机验收的项目。

## 9. 实机切换安排与回退条件

移植整体难度为中等；核心网页和数据库可复用，主要工作集中在进程生命周期、公开端口、开机会话和登录凭据。首版代码与自动化验证已经完成；余下时间取决于目标主机、软件下载网络和人工网站登录。

| 阶段 | 预估时间 | 操作与放行条件 |
| --- | --- | --- |
| 主机准备 | 2–4 小时 | 安装依赖、专用用户、磁盘目录、普通用户 sandbox、固定显示；doctor 无配置错误 |
| 单实例试迁 | 2–4 小时 | 导入元数据、重新登录、核验目录与 PID、从另一台主机验证 CDP 指令 |
| 三实例并发 | 半天 | 三个调用项目使用不同端口同时运行，演练 Web 重启、Chrome 重启、端口冲突与调用超时 |
| 稳定观察 | 至少 48 小时 | 检查状态一致性、重连、资源和日志增长；无未解释的中断后再正式切换 |
| 正式切换 | 30–60 分钟 | 暂停 Windows 任务，保存进度，将调用地址切到 Ubuntu IP，逐项恢复并核验结果 |

以上为部署估算，不包含网站审核、复杂验证码和业务项目自身故障。未完成验收时保留 Windows 为可回退环境。

调用方应将 `http://Windows-IP:端口` 改为 `http://Ubuntu-IP:相同端口`，不要固定旧浏览器的 WebSocket UUID；每次重连重新读取 `/json/version`。主机重启和 Chrome 重启都会中断旧连接，调用方需使用有上限的退避重连，并先核对业务步骤是否已提交，再决定是否重试。

出现目录身份不匹配、公开 CDP 持续不可用、业务重复提交或登录无法保持时暂停切换；保存 Ubuntu 日志和故障时间，停止对应 Linux 业务任务，将调用地址切回仍保留的 Windows 环境。回退不覆盖两个平台的 Profile，不合并运行数据库，不同时让两套环境执行同一账户任务。
